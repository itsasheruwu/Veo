# Browser implementation boundary

The pinned Swift source is `Veo/Models/DesktopBrowserModel.swift` (workspace tabs, selected-tab restoration, viewport, console and downloads) and `Veo/Services/DesktopBrowserKeychain.swift` (password offers, credential choice, HTTP authentication and client certificates). Browser settings have five model switches; restore-tabs defaults off in `DesktopUtilityPreferences`.

The Windows browser uses one WebView2 profile under the selected Veo data root. Native tab IDs/order/selection are retained per canonical workspace, with cross-launch restoration gated by the existing restore-tabs preference. A separate versioned browser store holds desktop layout and workspace viewport choices without changing the shared preferences schema.

Credential save/fill requires an explicit native action and exact scheme/host/port agreement between the captured message, current top-level document and action completion. Passwords reside in current-user Windows Credential Manager; the browser metadata index contains account names and origins, never secrets. HTTP authentication uses a distinct realm-specific key. Client-certificate choice is delegated to WebView2's native certificate dialog. Actual passkey registration and real account sign-in remain Pending.

Local previews use a unique synthetic HTTPS origin per tab and a read-only request adapter rather than unrestricted file navigation or folder mapping. Reads are bounded, allowlisted by MIME, and validate the opened file's final handle path against the opened workspace directory's final path. Traversal, alternate streams, unsupported types, network escape and junction escape are rejected. Host objects are disabled. Preview pages receive a restrictive response CSP and no native host method access.

Downloads resolve the Downloads Known Folder, reserve a sanitized noncolliding filename, expose progress/cancel, and enable open/reveal only after opening the completed destination and reading its bytes/hash. Tests must cover collision, origin/realm mismatch, unsafe names, restore selection/order, traversal, oversize, outside-root and junction rejection. Native click, real download, HTTP-auth/certificate UI, physical permission prompts, WebAuthn and embedded account login still require app workflow evidence.

API references: [WebView2 local content](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/working-with-local-content), [HTTP authentication](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/basic-authentication), [native client certificate dialog](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2.clientcertificaterequested), [WebResourceRequested](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/webresourcerequested).

## Verified Windows browser checks

`dotnet run --project windows/tests/Veo.Browser.Tests -- --credentials` passed 28 checks in the normal current-user Windows context on 2026-11-17. Checks include origin scheme/host/port separation, embedded-credential rejection, localhost/IPv4/IPv6 routing, stable tab identity/order/selection/viewport readback, restoration opt-in and workspace isolation, reserved filename collision, actual completed-file bytes and SHA256, synthetic-origin resolution, encoded traversal, outside-root and actual junction final-handle rejection, resource size/MIME/alternate-stream rejection, explicit save confirmation, real disposable form and realm-specific HTTP credentials, different-port/origin refusal, secret-free metadata, and credential deletion/absence. No physical account credentials were used.

`Veo.Browser.Tests --serve --port=40972` is a bounded loopback TCP HTTP fixture for native app verification. It offers a 32,821-byte exact download (SHA256 `E3B562D53AD9BB1570A178F7D6141F220C5D3E5D813999A9EE81B4098D997792`), slow download/cancellation, Basic authentication using disposable fixture text, same-origin password form, popup and console output. Running service tests or starting this fixture does not establish native UI parity.
